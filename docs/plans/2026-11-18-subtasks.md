# Subtasks: a list to tick off under a task

Fixes #11.
Branch `feat/subtasks` · Worktree `../done-wt/subtasks` · Base `origin/main` @ 1fc3741 (2026-11-18)
Status: implemented, PR open, not merged. The nine decisions are still UNCONFIRMED. Size: standard plan — the shape is known, the choices below are real.

## Outcome

A task can hold subtasks. The parent's row shows how many are done and expands to list them, each with its own check, title and notes, and a field to add another. An agent can add a task with its subtasks in one call. The first use is one task per messaging platform with one subtask per person waiting on a reply.

## Evidence (verified, do not re-derive)

- `crates/core/src/lib.rs` is the only code touching SQLite. Tasks are saved through `sync(Change)` under one revision; new columns are added in `Store::open` (see `goal_day`).
- `Store::state(today)` sends open tasks and tasks finished today only. A subtask ticked yesterday would vanish from its still-open parent unless the query changes.
- `PRAGMA foreign_keys = ON` is set, and `sync` writes tasks in the order the window sent them, which is id order from the picture, not parent-first by guarantee.
- The interface builds every list from `sections`, `counts`, `lanes`, `timelineGroups`, `clearsToday` (`ui/src/lib/tasks.ts`) and `focusTasks` (`ui/src/lib/focus.ts`). `changes.ts` diffs whole task objects, so a new field on `Task` is saved without touching it.
- `deleteTask` in `tasks.ts` removes one task and returns an undo that splices it back.
- The MCP server's `open_task` finds any open task by id, so update, complete and delete already reach a subtask once it is in `State`.
- The installed app reads tasks with a named column list, so it ignores a column it does not know; it would show subtasks as ordinary tasks until it is updated.

## Decisions

1. **What a subtask is** — *a task with `parent_id`*, so checks, notes, undo, sync and MCP all work on it as they do on any task. Alternative: a checklist stored as text in the parent's notes (nothing to sync, but no ids for an agent and no undo per line).
2. **Depth** — *one level.* A subtask cannot have subtasks; a task that has them cannot become one.
3. **Where they show** — *only under their parent.* Not in Inbox, Today, Upcoming, Board, Timeline, the sidebar counts or the Focus pickers.
4. **Ticked subtasks** — *stay under an open parent, struck through*, however long ago they were ticked.
5. **Finishing a parent** — *finishes its open subtasks too.* Reopening the parent (Undo) reopens the ones that were finished with it.
6. **Deleting a parent** — *deletes its subtasks*; Undo restores all of them.
7. **Expanded or collapsed** — *collapsed by default*, remembered per window in browser storage.
8. **MCP** — *`add_task` takes `subtasks` (a list of title and notes) and `parent` (an id); `list_tasks` nests subtasks under their task.* No new tools.
9. **Not in this version** — dragging to reorder, dates and priority shown on a subtask's row, turning a task into a subtask by dragging.

UNCONFIRMED: all nine were shown to the owner as defaults on 2026-11-18 and built without waiting for an answer, because the owner asked for the feature to be built the same evening.

## Design

### Core (`crates/core/src/lib.rs`)

- `Task.parent_id: Option<i64>` (`parentId` over JSON, default none).
- Column `parent_id INTEGER REFERENCES task(id) ON DELETE CASCADE`, in `CREATE TABLE` and added to an older file in `Store::open` the way `goal_day` is.
- `state(today)` also sends every subtask of an open task, finished or not.
- `sync`: foreign keys are checked at commit (`PRAGMA defer_foreign_keys`), so a parent and its subtasks can arrive in any order in one change. After the writes, the change is refused as `Invalid` if any subtask's parent is itself a subtask.

### MCP (`crates/mcp/src/lib.rs`)

- `add_task`: `parent` (integer) makes it a subtask of that open task; `subtasks` (array of `{ title, notes? }`) adds them under the new task, with ids following it. Both together are refused.
- `list_tasks`: top-level tasks only, each with `subtasks: [{ id, title, notes, done }]`. Filters apply to the parent.
- `complete_task` on a parent finishes its open subtasks in the same change.
- `describe` includes `parent` for a subtask.

### Interface

- `ui/src/lib/tasks.ts`
  - `Task.parentId?: number | null`.
  - `subtasksOf(tasks, id): Task[]` in id order; `progress(tasks, id): { done, total } | null`.
  - `openTasks` leaves subtasks out, which removes them from every list, count, lane, timeline group and focus picker at once. `lanes().done` leaves them out too.
  - `addSubtask(data, parentId, title): Data` — takes the parent's project.
  - `markDone` on a parent finishes its open subtasks on the same day; `markOpen` reopens those sharing the parent's `doneDay`.
  - `deleteTask` removes the subtasks with the parent and its undo restores them in place.
- `ui/src/lib/expanded.ts` — which parents are open, in localStorage `done-expanded`; reads and writes survive storage being unavailable.
- `ui/src/components/subtasks.tsx` — the list under a parent: check, title, notes, an "Add subtask" field that keeps focus so several can be typed in a row.
- `ui/src/components/task-row.tsx` — a chevron and "done/total" on a row with subtasks; the list under it when expanded.
- `ui/src/components/task-editor.tsx` — no project field for a subtask.
- `ui/src/components/app-menu.tsx` — "Add subtask" on a top-level task's menu.

### Invariants

- A subtask's parent is never a subtask.
- A subtask is never listed without its parent.
- Deleting a parent leaves no row pointing at it, in the file or on screen.

## Tests

- Core: a subtask ticked on an earlier day still comes back under its open parent, and stops coming once the parent is finished on an earlier day; a parent and subtask saved in one change in child-first order are accepted; a subtask of a subtask is refused and nothing is saved; deleting the parent deletes the subtasks; a file without the column gains it on open.
- MCP: `add_task` with `subtasks` is listed nested with their notes; completing one subtask shows it as done under the parent; completing the parent removes both from the list.
- Interface logic: subtasks are absent from sections, counts, lanes and timeline groups; `markDone` on a parent finishes open subtasks and `markOpen` brings back only those; `deleteTask` on a parent and its undo.

## Out of scope

Reordering; nesting deeper than one level; subtasks on the Board or Timeline; due dates shown on a subtask's row.

## Execution notes

- Plan vs built: Core, MCP, Interface and Invariants MATCH, with the three rulings below.
- Ruling: a subtask's project is set when it is added and not kept in step when its task moves — nothing reads it, since a subtask is only shown under its task — cost if wrong: a project's subtasks fall to no project when the project is deleted, which is invisible.
- Ruling: a subtask naming a task that does not exist is refused as `Invalid`, by turning the deferred foreign-key failure at commit into that error — cost if wrong: any other constraint failure at commit would carry the same message; there is no other constraint on these tables that can fail there.
- Ruling: the right-click menu on a subtask offers Edit, Complete and Delete only, and "Add subtask" on a task opens its list — a subtask has no date, priority or project to choose — cost if wrong: those fields are still reachable in the editor.
- Ruling: a ticked subtask does not fade out like a task's row; it stays, struck through, and its check reopens it.
- Verified: `npm run typecheck`, 393 interface tests, `npm run build`, `cargo test -p done-core -p done-mcp -p done-server` (18). Fail-first: removing the subtask clause from `state` and removing the deferred foreign-key check each fail `a_subtask_ticked_days_ago_stays_under_its_open_task`; putting subtasks back into `openTasks` fails "are shown under their task and nowhere on their own".
- Verified in a browser against a copy of the owner's tasks file: the count on the row, expanding, ticking a subtask, adding one with the field (shortcut keys typed into it stay text), and the sidebar count rising by one for a task with three subtasks.
